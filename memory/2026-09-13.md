# 13.09.2026

- **git-push-Hänger endlich gelöst — war nie ein Netzwerkproblem:** Nach dem `wsl --shutdown` erneut getestet, hing weiter trotz allem bisherigen Aufwand. Systematisch durchprobiert: Checksum-Offload auf Windows-Adapter (physisch + vEthernet-WSL) deaktiviert, `http.version HTTP/1.1` erzwungen, Large Send Offload v2 + Receive Segment Coalescing auf dem vEthernet-WSL-Adapter aus, TSO/GSO/GRO auf WSL-eigenem `eth0` aus, WISO Internet Security (F-Secure-Engine) testweise 15 Min. pausiert — alles ergebnislos, jede Einzelmaßnahme fühlte sich nach dem richtigen Verdächtigen an, war es aber nicht.
- **Echte Ursache:** Direkter curl-Test gegen den echten GitHub-Endpunkt (chunked POST, mit echten Zugangsdaten) antwortete in 0,35s — kein Netzwerkfehler. Der `/proc/<pid>/io`-Zähler des laufenden `pack-objects`-Prozesses zeigte dann den entscheidenden Hinweis: 500MB+ bereits in die Pipe geschrieben, für einen angeblich 9KB kleinen Push. Ursache: Die automatische Nachtsicherung vom 09.09.2026 hatte trotz vorhandener `.gitignore`-Regel zwei riesige Backup-tar-Dateien (Robin-Tansania-Reorg 1,6GB + Kilimanjaro-WhatsApp-Backup 212MB) versehentlich in einen Commit gezogen. Jeder Push seither versuchte, ~1,8GB hochzuladen — sah bei kurzen Testtimeouts wie ein Hänger aus.
- **Fix:** Interactive Rebase auf den betroffenen (noch ungepushten) Commit, beide Dateien per `git rm --cached` aus der Historie entfernt (liegen unverändert auf der Platte weiter). Push danach: 9KB, 4 Sekunden. `scripts/nacht_backup.sh` gehärtet — `git add` schließt `backups/*.tar` jetzt explizit per Pathspec aus, plus generisches Sicherheitsnetz verwirft automatisch jede gestagte Datei >20MB vor dem Commit. Alle Windows/WSL-Netzwerk-Einstellungen wieder auf Standard zurückgesetzt, da nachweislich nicht die Ursache. 18+ Commits erfolgreich auf GitHub gepusht.
- **Lehre für künftige ähnliche Fälle:** Vor jeder Netzwerk-Ferndiagnose bei „git push hängt" zuerst `git rev-list origin/master..HEAD --objects | git cat-file --batch-check='%(objecttype) %(objectsize) %(rest)' | sort -k2 -nr | head` prüfen — zeigt sofort, ob ein Riesen-Blob im Spiel ist.
